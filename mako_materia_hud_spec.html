01先判断是否需要自己写

在动手写代码之前，实现者应该先花半小时验证现成方案能否直接吃下这套结构。这一步做对了，整份文档可能就只剩参考价值。

ZK 生态的标准神器 HUD 是 EntWatch-4（srcdslab/sm-plugin-entwatch-4）。它有两代配置形态，其中新一代和本图结构相当接近：

形态路径item 建模方式与本图的距离
旧 configs/entwatch/<game>/*.cfg item = 武器 hammerid + buttons{hammerid,type,mode,maxuses,cooldown} 本图没有"神器武器"，不匹配
新 configs/entwatch/maps/*.cfg item = buttonclass + filtername + pt_spawner + mode/maxuses/cooldown 和"拾取 trigger + 施法 button + point_template 挂件"几乎一一对应

EntWatch-4 只依赖 sdktools 的 entity output 与 SDKHooks，L4D2 两者都有。所以第一步是在本机 L4D2 上装 EntWatch-4，把新形态配置喂给它试跑。能跑通就配置化收工；不能跑通，再按下文自写，并且此时你已经通过实验知道了哪些 hook 拿不到数据——这比先写状态机再去猜要快得多。

02已确证的地图事实

以下全部来自对地图文件的直接读取，不是推测。来源与取证方式：workshop 包 1794251408.vpk 内的 maps/l4d2_ffvii_makoreactor.bsp（VBSP v21，mapRevision 7002）；VScript 在 scripts/vscripts/ffvii_makoreactor/；实体清单由 BSP entity lump 解出后与 bspsrc 反编译的 VMF 交叉核对。

取证注意

CS:S 自带的 vpk.exe 解这张 L4D2 BSP 会得到错误字节（文件头不是 VBSP，CRC 与包内记录不符）。实现者若要自己取证，需要按 VPK v1 目录树直接读条目偏移，或用 64 位版 vpk 工具；不要直接用旧 vpk.exe 的结果做反编译，会得到"文件损坏"的假结论。

每个 Materia 还各有一个 point_template（M_<X>_ParentSpwn）与一个 logic_script（M_<X>_ParentScr，跑 materia_parent.nut 的 Think()）用来把挂件跟随到玩家身上。Verified

2.2拾取与归属（关键坑）

每个 M_<X>_Trigger 是 trigger_multiple，过滤器 MateriaFilter 是 filter_activator_name，目标名 SurvivorHuman。所以只有人类幸存者能拿，bot 被过滤掉——HUD 天然只需面对人类。Verified

触碰时地图的 I/O 链：

  • OnStartTouch（delay 0）→ InitializePickMateria(N)：把编号写进玩家脚本域的 PretendMateria。
  • OnStartTouch（delay 0.01）→ TryParentMateria(N)：找到第一个 PretendMateria == N 且 HasMateria == false 的幸存者，把该玩家 targetname 改成 Carrier<X>；0.25 秒后再改成通用的 MateriaCarrier；然后 ForceSpawn 对应的 ParentSpwn；置 HasMateria = true；break（一人一份）。
这是最容易写错的一处

不要用玩家 m_iName 做持有人来源。写成 CarrierFire 的窗口只有约 0.25 秒，之后统一变 MateriaCarrier，而这个名字不携带"哪一块"。更麻烦的是地图侧还有重命名循环：Button_master 的 OnPressed 会启用 Survivor_renamer_loop，对应 RenameSurvivors() 把非 carrier 的人类刷成 SurvivorHuman，bot 刷成 SurvivorBot。

可靠做法是用"触碰了哪一个 trigger"来归属：trigger 本身是按 Materia 分的，caller 的 targetname 决定是哪一块，activator 就是持有人。名字只能当辅助校验。

2.3施法与冷却

M_<X>_Button 是 func_button_timed，use_time 1.5（Ultima 是 2.0）。OnTimeUp 才是"施法完成"的信号，不是按下的瞬间——玩家中途松手不会触发。Verified

MateriaT1T2T3冷却写在哪
Fire70110150M_Fire_Logic_Tn OnTrigger → M_Fire_Button Enable <delay>
Ice6090120M_Ice_Logic_Tn OnTrigger → M_Ice_Button Enable
Heal90150210M_Heal_Logic_Tn OnTrigger → M_Heal_Button Enable
Shield90150180M_Shield_Logic_Tn OnTrigger → M_Shield_Button Enable；同时置 ShieldCount

Void固定 110M_Void_Logic OnTrigger → M_Void_Button Enable 110
Ultima一次性OnTimeUp → !self Kill 1；按钮自毁，无法再用

几个附带细节：Ultima 的 use_sub_string 就写着 "Only 1 use, do it wisely!!"，且 OnTimeUp 里调 FreeUser() 释放持有权，让该玩家可以再去拿别的。Void 的效果持续约 15 秒（M_Void_Loop Enable 后 14.9 秒 Disable），但按钮 110 秒才回来。Haste 的 OnTimeUp 触发 MHasteSpeed() 并播 5 秒特效。Verified

2.4Thunder 是充能制，不是冷却制

这一块和其他七种机制完全不同，HUD 必须单独处理。Verified

  • M_Thunder_ChargCount 是 math_counter，startvalue 3、max 3。OnHitMax 关掉再生计时器，OnHitMin 关掉按钮。
  • M_Thunder_Regeneration 是 logic_timer，RefireTime 50：每 50 秒 Add 1 并重新 Enable 按钮。
  • 每次施法：M_Thunder_logic_0N 的 OnTrigger Subtract 1（1/2/3 对应三档效果）。
  • 上限会随等级变：MateriaMasterCase 的 OnCase01 做 SetHitMax 1 + SetValueNoFire 1，OnCase02 做 SetHitMin 1。

结论：HUD 必须实时读 m_flMin / m_flMax / m_OutValue 算当前值和上限，绝不能把 3 写死。

2.5Shield 余量：唯一不能直接读的状态

ShieldCount 是 materia_core.nut 里的 VScript 全局变量。SourceMod 没有运行时读 Squirrel scope 的通道，也绝对不要去猜内存偏移读它。但好消息是：三条变更路径全部经过地图自己的 I/O，可以完整镜像。Verified

路径实体 / output数值
初始化M_Shield_Logic_T1 / T2 / T3 · OnTrigger25 / 40 / 50
自然衰减M_Shield_Timer（logic_timer, RefireTime 1）· OnTimer−1 / 秒
敌军触碰M_Shield_AntiCI_T1/T2/T3（trigger_multiple, filter_infected）· OnStartTouch见下
归零M_Shield_Script · OnUser1镜像清 0，停表

AntiCI 触发器上的 MShieldCheck() 分三档，照抄它的规则即可：

  • activator 类名是 infected（普通僵尸）→ −1
  • 否则是非幸存者玩家，且 GetZombieType() < 8 → −3
  • 否则（Tank）→ −6

镜像值降到 0 时显示 E，并在 M_Shield_Script 的 OnUser1 上同步关掉 active 标志（脚本归零时会 FireUser1 到自身，从而禁用计时器并清理 AntiCI 触发器）。

2.6等级

MateriaMasterCase 是一个 logic_case，Case01/02/03 分别启用 T1/T2/T3 的 relay 组。插件 hook 这个 case 的三个 output 就能得到当前等级 1/2/3，用来选 2.3 表里对应那一列的冷却值。Verified（case 的 Case 值与 OnCaseNN 输出内容直接可读）Verify（是否同一回合只 fire 一次，见 §4）

03插件设计

核心思路一句话：不碰地图，只在地图自己的 I/O 上挂只读观察者，用插件侧的一份镜像状态驱动 HUD。

3.1结构与 Hook 面

单文件 l4d2_mako_materia_hud.sp。仅当 GetCurrentMap() == "l4d2_ffvii_makoreactor" 时工作；其他地图在 OnMapStart 直接停机，HUD 定时器空转返回，零开销。

在 OnPluginStart 里按"类名 + output 名"全量挂，回调里用 targetname 过滤。这样不依赖任何实例句柄，也不需要提前知道实体索引：

classnameoutput用途
trigger_multipleOnStartTouch拾取归属 + Shield 触碰扣值（同一入口，按 caller 名分流）
func_button_timedOnTimeUp施法完成：Haste 冷却、Ultima 一次性
logic_relayOnTriggertier relay 冷却、M_Void_Logic、M_Thunder_Entimer
logic_timerOnTimerM_Shield_Timer 衰减、M_Thunder_Regeneration 充能
logic_scriptOnUser1M_Shield_Script 归零
logic_caseOnCase01/02/03MateriaMasterCase → 等级
math_counterOutValue · OnHitMaxThunder 充能变化

回调签名一律用返回 void 的形式（如 public void Output_X(const char[] output, int caller, int activator, float delay)）。返回 void 意味着永不拦截，地图的原行为逐字不变——这是本设计"纯观察"约束的技术保证。

另外在 OnMapStart 之后一帧（RequestFrame）扫一遍 MaxClients+1 → GetMaxEntities()，缓存三类 EntRef：各 M_<X>_Trigger、各 M_<X>_Button、M_Thunder_ChargCount。这些引用只用于反查和读 counter，实体自身的 output 仍然靠类名级 hook 接住。若要更省，可以再对这几个已知实例补 HookSingleEntityOutput。

3.2状态模型

全部状态都在插件里，大小不超过几百字节：

clientItem[65]每个玩家持有的编号，−1 = 无。用于释放与"一人一份"判定
readyAt[8]冷却结束时刻（GetGameTime() 基准），0 = 无冷却

死亡为什么不清持有人

materia_parent.nut 的 Think() 在玩家 IsDead() || IsDying() 时只把挂件挪到原点隐藏，并不清 PretendMateria / HasMateria；清空只发生在 FreeUser()，而它只被 Ultima 的 OnTimeUp 调用。也就是说玩家复活后仍然是持有人，挂件会回来。插件跟着这个语义走：死亡期间继续显示持有人（要不要变灰由实现者定），但不要清。

3.4状态字符串

行格式照抄 EntWatch-4 ew4/interface.inc 的原式，注意冒号后有一个空格："%s [%s]: %N" → 短名、状态、玩家名。多按钮时状态用 | 连接。Verified

玩家实际看到的画面是这样（KeyHintText，左侧中上，等宽字体）：

In-game HUD · 仅列已被拾取的条目 eriF [73]: 阿明 dleihS [22/40]: 阿杰 rednuhT [2/3|18]: 小王 amitlU [E]: 阿强 ↑ 未拾取的 Materia 不出现在面板上（EntWatch 范式）

短名按项目惯例用反写拼写（eriF / ecI / laeH / rednuhT / dleihS / etsaH / dioV / amitlU）。这是命名约定，不是地图事实；如果你们服务器另有习惯，以你们的为准，改一张常量表即可。

3.5HUD 渲染与分页

直接照搬 EntWatch-4 的分页机制，参数一致：

  • 只输出 holder[X] != 0 的行。
  • 缓冲 pages[8][255]，每页容量 255 − 8 = 247 字节（尾部 8 字节留给页码信息，与 EntWatch 原式相同）。行长按 strlen + 1 计（给换行留位）。按 UTF-8 字节数分页，不是按行数。
  • 单行超过整页容量就丢弃该行，不要截断。
  • 页数 > 1 时每 5 秒轮换一页；页首加 "%s%d/%d" 前缀（当前页 / 总页数），单页时不加。
  • 发送：StartMessageOne("KeyHintText", client)；protobuf 时 PbAddString(msg, "hints", text)，否则 BfWriteByte(msg, 1) + BfWriteString(msg, text)，最后 EndMessage()。
  • 刷新定时器 1.0 秒；跳过 IsFakeClient。
  • 面板变空时，对之前显示过的客户端补发一次空白串清屏（EntWatch 的做法）。
  • sm_hud 切换显示；持久化可以用 cookie（可选）。

EntWatch 的 3 个槽位（全部 / T / CT）在本图用不上——持有人全是幸存者，单槽就够——但 8 页预算机制保留，因为玩家名长度不可控。

3.6容错

  • 地图实体找不到（改图、换版本）→ 安静停机，不要报错刷屏。
  • 缓存任何 EntRef 之前先 IsValidEntity 验活。
  • 所有回调都要容错 caller / activator 为 −1 或非实体的情况。
  • 读 Thunder counter 前用 HasEntProp 探测 m_OutValue / m_flMin / m_flMax，缺一个就退化成 N/A。

04必须实测的开放问题

下面每一条都能在三十分钟内验证完。建议先用一个只有 HookEntityOutput + PrintToServer 的打点版插件把这些跑一遍，再写状态机。

  1. 拾取归属是否成立：OnStartTouch 的 activator 是否稳定为人类幸存者（过滤器是 MateriaFilter／SurvivorHuman）。若被过滤的玩家不进回调，改成轮询或改用 SDKHook_StartTouch。
  2. 玩家名被反复覆盖：确认 Survivor_renamer_loop 的实际影响。结论大概率是"不能用 m_iName 做长期归属"，但要亲眼看到。
  3. func_button_timed 的 OnTimeUp 是否带 activator：若带，Ultima 释放持有人可以精确定位到按键者；若不带（−1），就按"Ultima 用掉即释放"处理。
  4. GetZombieType() 与 m_zombieClass 的对应：护盾 −3 / −6 的分界是 < 8，实测 Tank 是否为 8。
  5. 等级来源：MateriaMasterCase 的 OnCase01/02/03 是否同一回合只 fire 一次；若多次，以最后一次为准。
  6. 回合语义：本图是 survival 模式（scripts/vscripts/survival.nut 与 l4d2_ffvii_makoreactor_survival.nut）。确认 round_start 会不会清空地图侧状态；插件按"不清持有人"实现，实测后按需要再改。
  7. EntWatch-4 能否直接吃下这套结构（见 §1）。能，则本插件作废，写配置即可。

05不做的事

这几条是本次分析里踩过或差点踩进去的坑，写下来防止实现者跑偏。

  • 不写 Squirrel 变量、不新增地图实体、不改 bsp / vpk。运行中的地图 VScript 没有从 SourceMod 侧写入的通道。
  • 不猜内存偏移去读 ShieldCount。它只能靠 I/O 事件镜像。
  • 不拦截、不改写任何原 output。回调返回 void，地图行为逐字不变。
  • 不把 Thunder 上限写死成 3。等级会改 m_flMax。
  • 不因为玩家死亡就清持有人。地图自己不清。
  • 不用 m_iName 作为长期持有人来源。它只在 0.25 秒窗口内可辨。
  • 不假设有"神器武器"。本图的神器是 trigger + button + point_template 的组合，不是双枪或任何武器实体。

06交付与验证

  • 产物：addons/sourcemod/scripting/l4d2_mako_materia_hud.sp，编译用 L4D2 自带的 spcomp.exe（或 64 位版）。只编译，不部署。
  • 本地验证：在 …\Left 4 Dead 2\left4dead2\addons\sourcemod\ 下临时 sm plugins load，进图逐项确认——8 行都出得来、拾取后出现、冷却倒数、Thunder 充能变化、护盾掉值、Ultima 变 E、多页轮播正常。
  • 顺序建议：先写打点版把 §4 全部跑完，再写状态机和 HUD。反过来做会多花好几倍时间。
